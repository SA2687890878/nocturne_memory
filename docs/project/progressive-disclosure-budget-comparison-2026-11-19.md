# 渐进式披露预算对照（2026-11-19）

## 方法

同一组 18 条人工压缩关键词查询，在真实工作库中分别以 `token_budget=0`（L0/导航元数据）和 `token_budget=1200`（允许摘要）执行严格检索。两组均关闭 PARTIAL 和正文片段。

## 指标

| 指标 | L0 / budget=0 | 摘要预算=1200 |
|---|---:|---:|
| 响应字符总数 | 8,004 | 10,537 |
| 服务端估算 Token 总数 | 3,144 | 5,459 |
| 有效摘要数 | 0 | 22 |
| 目标命中 | 18/18 | 18/18 |
| 候选集合一致 | — | 18/18 |

L0 相比摘要模式减少 **42.41% 服务端估算 Token**。两种模式的候选集合与目标命中完全一致。

## 结论

建议保持分层：
- 需要先定位记忆时用 L0。
- 需要判断候选是否相关时加载摘要。
- 需要代码、参数或历史细节时再读正文。

不要把 `token_budget=0` 作为所有任务的默认值；它减少判断上下文，应按任务阶段使用。

## 限制

服务端估算 Token 不是模型供应商真实 tokenizer，也不包含 Deva 客户端注入、system prompt 和其他工具开销；本实验不能直接代表端到端实际 Token 节省。
