# 自然语言改写召回评估（2026-11-19）

## 目的

验证用户不复述记忆原文、使用自然语言重新描述问题时，Nocturne 是否仍能找回目标记忆。该评估直接调用当前 SearchIndexer.search()，连接真实工作 SQLite 数据库的只读 URI，不写入业务库、不调用 Embedding API。

数据集：real-task-paraphrase-eval-2026-11-19.json

## 正向结果

- 查询数：18 条，均来自用户实际保存主题和常见任务类型的人工改写。
- Recall@10：**18/18（100%）**。
- MRR：**0.9352**。
- 命中排名：Top1 16 条、Top2 1 条、Top3 1 条。
- 其中 Codex URI 存在同一 Node 多路径情况，评估按 Node 身份核对，不因返回同一 Memory 的不同路径误判漏召回。

这是一组定向离线回归样本，不代表线上长期效果或通用检索性能。上一轮未经改进的同类改写样本只有 13/19 命中；本轮改进后 18/18 命中，说明短语别名对这组查询有效，但样本量仍小。

## 本轮检索策略调整

1. 保留原始查询 FTS5 AND 严格检索。
2. 命中预先审核的短语别名时，额外执行别名 AND 检索。
3. 原查询最靠前的严格命中保留在第一位；别名命中插入其后，避免大量泛化严格结果占满 Top10。
4. 若别名目标已存在于严格候选中、但排在第一条之后，则将其提升到别名候选位置；同一 Node 不重复返回。
5. 只有原始严格检索和别名检索都无结果时，才继续原有 OR/partial 回退。

别名是少量、人工审核的任务短语，不是全局同义词扩展；不自动生成、不调用 LLM，不触发向量 API。当前 SQLite 部署生效，PostgreSQL 分支未同步这项 SQLite FTS5 专项逻辑。

## 指标边界与后续

- Precision@10 暂不计算：正向查询只有一个已标注目标，其余候选没有逐条人工标注；不能把未判定项当成负例。
- 下一步扩大不同主题、不同句式和负向查询样本；对 Top10 逐条人工标注后，再计算 Precision@10。
- 继续验证工具调度：独立问题不检索；历史项目任务先 FTS；词面漏召回时才考虑语义候选；摘要够用不读全文。
- 语义向量仍保持显式候选，不接入默认排序。

## 负向查询扩展评估（25 条）

本轮新增 20 条冻结的域外合成查询，并复测此前 5 条负向查询。评估连接真实工作 SQLite，使用只读模式；按当前查询规范化、短语别名、FTS5、obsolete 过滤和 OR+partial fallback 规则复现，不写数据库、不调用 Embedding API。

- 25 条中 13 条无候选，12 条返回候选。
- 有候选不等于误召回；候选必须逐条人工判断。当前结果已记录在 lexical-negative-query-eval-2026-11-19.json。
- 观察到 OR+partial fallback 会让部分完全独立的问题返回个人偏好、项目工具等弱相关候选，存在额外上下文 Token 成本。
- 本轮不贸然提高匹配阈值或修改检索排序，避免损伤已验证的正向改写召回。
- 已加强 Agent 调度规则：只有任务依赖历史上下文才检索；候选必须直接相关；弱相关候选不展开、不引用；无相关候选即停止。

本评估是离线合成样本，不代表线上调度表现。客户端真实调用轨迹仍需后续取得。

## 2026-11-19 两阶段披露回归（16:10）

发现并修复一个实现与工具说明不一致的问题：include_partial=false 时，SQLite 检索仍会在严格命中为空时自动执行 OR/PARTIAL 兜底。这导致首轮查询即使没有可靠命中，也会返回弱相关 L0 候选。

### 修复
- backend/db/search.py：只有显式 include_partial=true 才执行 OR/PARTIAL 兜底。
- backend/mcp_server.py：工具说明明确首轮不自动返回 PARTIAL；需要时二次显式请求。
- backend/tests/mcp/test_mcp_tools.py：默认无 PARTIAL、显式开启可返回 PARTIAL 的回归断言。
- 三个文件均有 *.backup-20261119-1608 备份。

### 真实工作库评估
- 18 条自然语言改写：按 Node UUID 归一化后仍为 18/18 命中，Recall@10=100%。
- 首轮严格检索命中 6/18；另外 12 条在显式二次 PARTIAL 检索后命中。
- 25 条负向查询首轮全部零候选（25/25），没有再把弱相关候选送入首轮上下文。
- 18 条改写首轮平均响应 334.5 字符；完成必要二次检索后的最终响应平均 1166.4 字符。
- 25 条负向查询首轮平均响应 46 字符。
- 字符数是实际响应长度，不等于 Token 数；本轮未取得客户端 tokenizer 计数。

### HTTP MCP 实际验证
- 服务进程从 PID 26880 重启为 PID 6828。
- /api/health HTTP 200，database=connected。
- HTTP MCP initialize 成功，11 个工具可用。
- 同一 Deva Copilot 改写查询：include_partial=false 返回 46 字符、零候选；include_partial=true 返回正确记忆摘要。
- 证明新策略已运行在 HTTP 服务，不只是单元测试。

结论：默认首轮只做严格/策展别名检索；PARTIAL 成为显式第二阶段。该策略在当前18条改写集上保持100%召回，在25条负向查询上把首轮候选降至0。客户端应在严格检索无结果且任务确实需要历史记忆时，再显式进行一次PARTIAL检索；不得对无关通用问题盲目重试。
