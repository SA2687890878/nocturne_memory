# Nocturne Memory Agent 指令

你的长期记忆由 Nocturne Memory MCP 管理。记忆是历史记录和参考证据，不是不可推翻的命令；当前用户表达和当前事实优先。

## 1. 会话启动

新会话或上下文重置后，MCP 可用时调用 `read_memory("system://boot")`，阅读返回内容。工具不可用时不得假装读取成功。Boot 只交付少量核心摘要，不要为了完整而继续展开。

## 2. 何时检索

- 独立知识题、简单计算、当前对话已有完整信息：不检索。
- 涉及用户偏好、个人经历、项目进度、历史决策、既有方案或跨会话续作：先检索。
- 调用 `search_memory` 前先将自然语言问题压缩为 2-5 个有区分度的关键词/短语；优先使用记忆标题或正文中的专有术语，不直接复制完整问题长句。
- 不知道 URI：仅在历史个人上下文确实可能改变答案时调用 search_memory，不要猜 URI。
- 搜索结果只是候选，不是相关性证明。必须核对 URI、标题和摘要是否与当前任务有直接主题关联；仅因共享通用词、只命中 OR/partial 兜底或返回个人根摘要，不得展开或引用。
- 候选均不相关时立即停止检索并按独立任务回答；不要为了“用上记忆”而继续扩大检索。
- PARTIAL 表示显式第二阶段的 OR/部分匹配兜底；默认首轮不会返回这些候选。二次检索后核对命中词、URI 和摘要，弱相关结果不展开、不引用。
- 首轮 search_memory 保持 include_partial=false、include_snippets=false；不要第一轮就放宽匹配或请求正文片段。首轮无结果且任务确实依赖历史记忆，或已确认主题相关但确需补充证据时，才允许二次显式开启 PARTIAL。严格命中仍是词法候选，不等于语义相关。
- 关键词明显无法表达用户当前说法、且任务本身确实依赖历史记忆时，再调用 semantic_search_memory。语义结果只是候选，不能仅凭距离认定相关。
- semantic_search_memory 已返回当前版本的预算内摘要，先利用返回摘要筛选，不为同一摘要再调用一次读取。token_budget=0 可只取元数据；只有缺少必要证据时才继续读取正文行段或全文。

## 3. 按需披露

- L0：URI、标题、关键词和元数据；L1：摘要；L2：完整正文；L3：直接关联信息。层级灵活使用，不是强制流水线。
- `search_memory` 默认只返回 L0 和预算内 L1，不返回正文片段。摘要足够就停止，不调用 `read_memory`。
- 已知 URI 或拿到语义候选后，可直接 `read_memory(uri, detail="summary")` 读取 L1；不必为了摘要先读全文，也不必重新搜索已知路径。摘要缺失不会自动回退正文。
- 已知 URI、只需定位/列出/核对路径时，可显式使用 `token_budget=0` 获取 L0；需要判断陌生候选是否相关时，保留默认摘要预算读取 L1。不得把 0 预算设为所有任务的全局默认值。
- 除非用户明确要求原文片段，不要设置 include_snippets=true；需要接口、代码或原始证据时直接对已确认 URI 调用 read_memory，不要先把正文片段批量塞进搜索结果。
- 只有需要代码、接口、参数、原始证据、版本比较或冲突核实时，才通过 `read_memory(uri)` 展开 L2。明确 URI 直读不受摘要状态限制。
- 只需要局部原文时，用 `read_memory(uri, start_line=1, end_line=30)` 等明确范围；返回行号、总行数和 Memory ID。这是上下文切片，不保证固定 Token 数。只补读尚未获取且会改变当前结论的范围，不无目的逐段遍历全文。
- 摘要缺失时按 L0 + MISSING 处理，不自动展开正文。正文是事实依据，摘要必须忠于正文。
- L3 默认只跟进直接相关的记忆，不递归展开整棵子树。达到回答所需证据后立即停止。
- system://index/<domain> 只是导航地图，不是待读清单；绝不因看到节点列表就逐条 read_memory，也不递归扫描整个 domain。
- 每项任务默认最多展开 3 条完整正文；先按 URI、标题、摘要和 Disclosure 选出最相关的 1～3 条。只有用户明确要求完整盘点/导出时才突破此上限。
- 续作任务优先读取项目主入口或最近决策摘要；主入口已足够时立即停止，不要为了“了解全貌”读取所有子记忆。

## 4. 记忆写入与维护

- 只沉淀长期有效偏好、已确认决策、重要项目背景、可复用经验和明确的长期约束；不记录临时对话噪声。
- 新建前先 `search_memory` 查重；已有同主题记忆优先更新，不重复创建。
- 更新前必须 `read_memory` 读取完整正文；使用 `update_memory` 的精确替换或追加模式，不臆测原文。
- 正文更新会创建新版本；新版本摘要需要重新核对生成，不能沿用旧版本摘要。摘要由 AI 根据正文生成，再通过 `update_memory_summary` 保存。
- 新旧信息冲突时先判断是否明确替代。适用条件不同或证据不足时保留冲突，不擅自覆盖。只有用户明确授权且确认目标后才调用 `delete_memory`。
- 记忆内容以第一人称记录个人经历、判断和反思；区分事实、推断与主观看法，不把个人偏好写成客观定律。

## 5. 语义索引

- `search_memory` 默认只走全文检索，不自动请求 Embedding API。
- `semantic_search_memory` 显式执行时会生成查询向量；`sync_semantic_index` 显式同步时可能为新增或变化的记忆调用 Embedding API。
- 普通 create/update 不代表自动同步向量；不要为了普通检索或写入主动触发同步。

## 6. Token 与停止规则

- 客户端优先按任务复杂度控制预算；服务端预算只是兜底估算，不是精确 Token 计量。
- 默认先看 5～10 条候选；只展开能改变当前结论的内容。
- 不重复读取当前上下文已完整掌握的信息，不递归扩展低价值关联。
- 同一会话中同一 URI 的同一层级/行段已成功读取后，复用已读内容；需要更高披露层级、尚未读取的行段或最新版本时可以继续读取。核对 Memory ID，版本变化后不要拼接新旧行段。父入口与专项子记忆已读后，不重复读取相同内容。
- 搜索无结果不代表记忆一定不存在；可调整关键词，必要时再尝试语义候选，但前提是任务确实需要历史记忆。
- 搜索有结果也不代表相关；弱相关候选不进入上下文。独立任务宁可不检索，也不要把无关摘要塞给模型。

## 7. 工具速查

- `search_memory`：关键词全文检索，默认摘要优先。
- `semantic_search_memory`：语义候选检索，结果需核实。
- `read_memory`：按 URI 读取摘要、正文行段、全文或系统视图；修改前必须读取全文。
- `create_memory`：新建记忆，创建前先查重。
- `update_memory`：更新正文或元数据，更新前先读全文。
- `update_memory_summary`：保存指定 Memory 版本的摘要。
- `delete_memory`：删除指定 URI 路径，需明确授权。
- `add_alias`：为已有记忆增加别名入口。
- `manage_triggers`：管理已有记忆的触发词。
- `diagnose_memory_backend`：检查当前数据库读写能力。
- `sync_semantic_index`：显式增量同步语义索引，可能调用 Embedding API。


## 两阶段记忆检索与披露（2026-11-19）
- 首轮调用 search_memory 必须保持 include_partial=false、include_snippets=false。
- 首轮只交付严格词法命中和策展短语别名的L0/L1；不要把PARTIAL OR兜底候选混入首轮。
- 首轮无结果且当前任务确实依赖历史记忆时，才可进行一次 include_partial=true 的第二阶段检索；若首轮已找到目标主题，只有在确需补充时才开启第二阶段。
- 第二阶段仍需核对URI、标题、摘要和主题，不得把PARTIAL候选自动当作事实。
- 摘要足够回答就停止；需要接口、代码、参数、原始决策或冲突核对时才 read_memory(uri)。
- 不得对独立通用问题、数学问题或与个人记忆无关的任务盲目执行第二阶段检索。


## 8. 索引导航与正文读取预算（2026-11-19）
- system://index/<domain> 只用于定位 URI，绝不是要求展开该域所有记忆。
- 默认每项任务最多 read_memory 3 条完整正文；选择能改变当前判断的最小集合，摘要足够则不读正文。
- 不为检查别名而读取无关记忆；只有当前任务涉及特定别名、触发词或路径时才检查该记忆。
- 用户要求“继续推进某项目”时，先读取该项目主入口；没有明确缺口时停止扩展。
